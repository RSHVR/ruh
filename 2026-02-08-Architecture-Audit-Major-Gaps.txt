⏺ ★ Insight ─────────────────────────────────────
  Why combinatorial toxicity is architecturally significant for Ruh:

  1. It requires a different data model. Per-ingredient analysis is O(n) — check
   each ingredient against a database. Combinatorial analysis is O(n²) or worse
  — you need to check every pair (and potentially triplet) of ingredients. This
  means the current ingredient_matcher.py pattern of looking up individual
  ingredients won't scale here. Future implementation would likely need a
  graph-based approach where ingredients are nodes and known interactions are
  edges.
  2. Manufacturing context is a new data dimension. Ruh currently works with
  flat ingredient lists scraped from product pages. Manufacturing processes
  (temperature, order, packaging) are rarely on labels — sourcing this data
  would likely need the clinical partnerships and provenance tracking features
  from earlier in the roadmap, making these features build on each other.
  3. The "safe alone, dangerous together" pattern is genuinely one of the
  hardest problems in product safety. It's why the roadmap positions this after
  both provenance tracking and clinical partnerships — it needs the data
  infrastructure and domain expertise those features establish.

  ★ Insight ─────────────────────────────────────
  Why the DOM goes through 3 processes before it even touches the extension 
  boundary:

  1. Content script captures the DOM (content.ts:130) — this is the key
  architectural decision. The content script runs in the Amazon page's origin,
  meaning it has full access to the rendered DOM including JavaScript-generated
  content, the user's session cookies, and review pages. A server-side scraper
  would see Amazon's bot-detection page instead.
  2. Content script can't call the API directly — Chrome's Private Network
  Access (PNA) policy blocks requests from amazon.ca origin to localhost. The
  background service worker runs in chrome-extension:// origin, which is exempt.
   This is why there's a seemingly redundant relay through background.ts.
  3. The ~2MB→20KB compression happens server-side, not client-side — the full
  DOM is sent over the wire, then AmazonScraper.process_client_html() strips it
  down using CSS selectors. This is a deliberate tradeoff: sending 2MB costs
  bandwidth but guarantees the server has everything it might need. If
  compression happened client-side, a selector bug would mean missing data with
  no recovery path.
  ─────────────────────────────────────────────────

⏺ Here's the full picture on how confidence gets set:

  The short answer: Claude makes it up

  There is no formula, no heuristic, no post-processing. The confidence value is
   a free-form float that Claude generates as part of its JSON output, guided
  only by prompt instructions and Pydantic validation bounds.

  ---
  Where it's specified

  The system prompt (claude_agent.py:948-986) defines the output JSON schema and
   includes "confidence": 0.0-1.0 at three levels:

  Per-allergen:    "confidence": 0.0-1.0    (line 959)
  Per-PFAS:        "confidence": 0.0-1.0    (line 970)
  Per-concern:     "confidence": 0.0-1.0    (line 978)
  Overall:         "confidence": 0.0-1.0    (line 985)

  That's it. The prompt says 0.0-1.0 with no further guidance on what
  constitutes 0.3 vs 0.7 vs 0.95. Claude interprets this based on its own
  judgment of the evidence.

  What shapes Claude's decision

  Claude's confidence is implicitly influenced by these factors in the prompt,
  though none explicitly map to a number:

  1. Source quality constraints — the prompt heavily restricts what Claude
  should trust (claude_agent.py:943-946):
  ONLY use credible sources: .gov, .edu, manufacturer official sites,
  peer-reviewed journals, court records
  1. If Claude only found a blog post, it would likely assign lower confidence.
  If it found an FDA recall, higher.
  2. Knowledge base matching rules — allergens and PFAS must match the database
  (claude_agent.py:988-998). The prompt says if something isn't in the KB, it
  goes to other_concerns with category="under_investigation" and severity="low".
   This implicitly pushes unverified findings toward lower confidence.
  3. Incomplete ingredient lists — the prompt mentions (claude_agent.py:516):
  If ingredients aren't fully listed, note lower confidence
  4. The web search results themselves — if Claude searched for "BHT IARC 
  classification" and got clear results (IARC Group 2B), it would assign high
  confidence. If results were ambiguous or contradictory, lower.

  What validates it after the fact

  The Pydantic schema in extraction_schemas.py:251 provides a hard clamp:

  class AllergenDetected(BaseModel):
      confidence: float = Field(default=0.5, ge=0.0, le=1.0)

  This means:
  - If Claude outputs 1.5 → Pydantic clamps or rejects it
  - If Claude omits confidence → defaults to 0.5
  - If Claude outputs -0.1 → rejected

  The same constraint exists for PfasDetected (line 260), OtherConcern (line
  269), and the overall analysis confidence (line 308-313).

  How it flows into scoring

  Looking at harm_calculator.py:88-89:
  confidence = allergen.get("confidence", 1.0)
  contribution = points * confidence

  Note the fallback is 1.0, not 0.5. If confidence is missing from the dict
  (bypassing Pydantic), the allergen gets full weight. This is a
  conservative/precautionary default — "if we don't know how confident we are,
  assume it's real."

  ★ Insight ─────────────────────────────────────
  This is a common pattern in LLM-based systems and a real weakness.

  There's no calibration mechanism here. Claude could consistently output 0.85
  for everything regardless of actual evidence quality, and nothing in the
  pipeline would catch that. The system trusts Claude's self-reported confidence
   as if it were a calibrated probability, but it's really just a vibes-based
  float.

  Three things that would improve this:

  1. Calibration data: Log Claude's confidence alongside whether the validation
  logger later confirms or contradicts the finding. Over time, you'd see "when
  Claude says 0.8, it's actually right 60% of the time" — and could apply a
  correction curve.
  2. Evidence-based confidence: Instead of asking Claude for a float, ask it to
  cite the source type (FDA recall vs. blog post vs. PubMed study) and compute
  confidence deterministically from source credibility. The research_sources
  field at line 980-984 already captures this data — it's just not wired into
  the confidence calculation.
  3. The Pydantic default of 0.5 vs harm_calculator fallback of 1.0: These
  disagree. If Pydantic validation passes, you get 0.5 for missing confidence.
  If raw JSON is used (Pydantic fails at line 586), dict.get("confidence", 1.0)
  gives 1.0. Same missing data, different impact on the score.

  Hop 8 — Backend serializes response (analyze.py:674-682)

  Hop 9 — Background stores to chrome.storage (background.ts:191-213)

  This is the critical relay. The background worker does two things with the
  response:
  1. Pre-computes harmScore = 100 - data.analysis.overall_score and stores it
  2. Writes the entire response into chrome.storage.local under key
  analysis_${tabId}

  chrome.storage.local.set({
    [`analysis_${tabId}`]: {
      tabId,
      productUrl: message.productUrl,
      status: 'complete',

  Then sends the data back to content.ts via sendResponse.

  ★ Insight ─────────────────────────────────────
  chrome.storage.local is the shared state bus. The background writes, the
  content script reads the sendResponse, and the side panel reads
  chrome.storage. This is a deliberate decoupling — the side panel doesn't need
  to be open when the analysis completes. The data sits in storage until the
  user clicks the donut. If the side panel is already open, it picks up the
  change via chrome.storage.onChanged listener at
  SidePanelContainer.svelte:47-56, triggering a reactive update without any
  explicit message passing.

  ★ Insight ─────────────────────────────────────
  The ingredient grid does live cross-referencing at render time
  (AnalysisView.svelte:155-185). For each ingredient in the list, it checks
  whether that ingredient name appears in allergens_detected, pfas_detected, or
  other_concerns — using bidirectional substring matching. This means the badge
  color is computed on-the-fly in the template, not stored in the data. The four
   badge states:

  - badge-allergen (red-tinted): ingredient matches an allergen name
  - badge-pfas (amber-tinted): ingredient matches a PFAS compound
  - badge-safe (green-tinted): no matches and zero total findings (nothing bad

  is fine but others aren't)

  That last distinction is subtle — badge-safe only shows when the entire 
  product is clean, not just this individual ingredient. An ingredient that's
  not flagged in a product with allergens gets badge-unknown, not badge-safe.

  And the domain model ProductAnalysis in models.py:49-69 has no

  # models.py:139

  But the extension's AnalysisResponse type doesn't have the field:
