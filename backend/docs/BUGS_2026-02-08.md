## BUG-1: `research_sources` dropped at backend model boundary

**Severity**: High — consumer evidence is paid for but never shown
**Location**: `backend/src/api/routes/analyze.py:514-527`, `backend/src/domain/models.py:49-69`

**What happens**: Claude's agent performs consumer web searches (Reddit, forums) and returns findings in `research_sources` — a list of `{type, url, finding}` objects. The Pydantic schema `ProductSafetyAnalysis` in `extraction_schemas.py:304-307` validates this field. But when `analyze.py` builds the `ProductAnalysis` response model, it never maps `research_sources`:

```python
# analyze.py:514-527 — research_sources is NOT included
analysis = ProductAnalysis(
    allergens_detected=analysis_data.get("allergens_detected", []),
    pfas_detected=analysis_data.get("pfas_detected", []),
    other_concerns=analysis_data.get("other_concerns", []),
    # ← no research_sources
)
```

The domain model `ProductAnalysis` in `models.py` has no `research_sources` field at all. The data exists in `analysis_data` but is silently discarded.

**Evidence from logs**: Claude executed 3 consumer searches for the Paula's Choice product (lines 73, 163, 201), returning 15 Reddit/consumer results costing $0.024 in Tavily fees. None of this evidence reaches the user.

**Impact**: Users see "BHT — endocrine disruptor, moderate severity" but never see "47 Reddit users reported skin irritation" alongside it. The consumer evidence shapes Claude's findings indirectly but isn't shown as supporting evidence.

**Fix**: Add `research_sources: list[dict] = []` to `ProductAnalysis` model, map it in `analyze.py`, add to extension types, render in `AnalysisView.svelte`.

## BUG-3: Review parsing divergence — AmazonScraper finds reviews, review_vector_service doesn't

**Severity**: Critical — entire review analysis pipeline silently fails
**Location**: `backend/src/infrastructure/scrapers/amazon.py` vs `backend/src/infrastructure/review_vector_service.py`

**What happens**: Two different parsers look at the same HTML and disagree:

1. `AmazonScraper._extract_reviews_structured()` uses its own CSS selectors, finds reviews, extracts them to clean text. Log line 26: `Found 13 reviews embedded in product page`.

2. `review_vector_service.store_reviews()` looks for `data-hook="review"` divs via BeautifulSoup, finds 0. Log line 380: `BeautifulSoup found 0 total review divs across all chunks`.

The string match at log line 378 confirms the divs exist in the raw HTML: `13 data-hook='review' string matches`. But BeautifulSoup's DOM parser finds 0.

**Evidence from logs** (both products in session):

```
Product 1 (Paula's Choice BHA):
  Line 26:  Found 13 reviews embedded in product page
  Line 380: BeautifulSoup found 0 total review divs across all chunks
  Line 387: SKIP STEP 8: No reviews stored (reviews_stored=0 or None)

Product 2 (Paula's Choice AHA):
  Line 398: Found 8 reviews embedded in product page
  Line 616: reviews_stored = 0
  Line 617: SKIP STEP 8: No reviews stored (reviews_stored=0 or None)
```

**Likely cause**: The HTML chunking step (`Split into 1 page chunks` at line 379) may be breaking the DOM tree in a way that orphans the review elements, or the review divs are inside malformed/nested HTML that string regex catches but BeautifulSoup's strict parser rejects.

**Impact**: The entire review pipeline (Cohere embedding → semantic search → Claude health analysis) is dead. Step 8 is always skipped. `review_insights` is always `None`. Even if BUG-2 were fixed, there would be nothing to display.

**Fix**: Investigate why `review_vector_service` can't parse the same HTML that `AmazonScraper` successfully extracts from. Consider passing `AmazonScraper`'s already-extracted review text to the vector service instead of re-parsing raw HTML.

## BUG-5: Section parser extracts 0 ingredients from products that have them

**Severity**: High — bypasses the entire cost-saving DB matching pipeline
**Location**: `backend/src/infrastructure/section_parser.py`

**What happens**: The section parser is the first extraction step (free, no LLM). For the Paula's Choice BHA product (which has a well-known, publicly documented ingredient list), it extracted 0 ingredients:

```
Line 37: Section parser: Paula's Choice SKIN PERFECTING 2% BHA... (0 ingredients, 0 materials, 60% confidence)
Line 39: Method: section_parser, 0 ingredients
Line 41: Matching 0 ingredients and 0 materials against databases
```

Despite returning 60% confidence (above the 50% threshold), the parser found no ingredients. This means:

- **Step 1/3 (DB matching)** matched nothing — 0 allergens, 0 PFAS, 0 toxic substances
- **Step 2/3 (classification)** classified 0 safe, 0 known concerns, 0 need research
- **Step 3/3 (Claude)** received no pre-classified ingredient data, had to find ingredients itself via web_search

The entire cost-saving pipeline (extract locally → match DB → only send unknowns to Claude) was bypassed. Claude ran 8 iterations and 21 web searches ($0.144 in search costs alone) partly because it had to discover the ingredient list from scratch.

**Impact**: ~$0.45 per analysis instead of the ~$0.10-0.15 target. The DB matching step that would have caught known allergens/PFAS for free contributed nothing.

**Fix**: Investigate why `section_parser.parse_sections()` fails to extract ingredients from `=== section ===` formatted text that contains ingredient data. The `AmazonScraper` extracted the product_attributes section (which typically contains ingredients on Amazon), so the data is in the text — the parser just isn't finding it.

## BUG-6: Confidence value disagreement between Pydantic default and harm_calculator fallback

**Severity**: Low — edge case, but produces inconsistent scoring
**Location**: `backend/src/domain/extraction_schemas.py:251,260,269`, `backend/src/domain/harm_calculator.py:88`

**What happens**: Two different defaults are used for missing confidence values:

```python
# extraction_schemas.py — Pydantic schema default
class AllergenDetected(BaseModel):
    confidence: float = Field(default=0.5, ...)  # ← defaults to 0.5

# harm_calculator.py:88 — scoring fallback
confidence = allergen.get("confidence", 1.0)  # ← defaults to 1.0
```

If Pydantic validation passes (`_parse_response` at `claude_agent.py:582`), a missing confidence gets `0.5`. An allergen worth 18 base points contributes `18 * 0.5 = 9 points`.

If Pydantic validation fails (line 586, raw JSON used), `dict.get("confidence", 1.0)` gives `1.0`. The same allergen contributes `18 * 1.0 = 18 points` — double the score.

**Impact**: Same missing data produces different harm scores depending on whether Pydantic validation succeeds or fails. A product could score 30 (Safe) via one path and 45 (Moderate Risk) via the other.

**Fix**: Align defaults. Either change `harm_calculator.py` to use `0.5` as the fallback, or change the Pydantic default to `1.0` (precautionary). The precautionary approach (`1.0`) is more consistent with the existing philosophy at `harm_calculator.py:130-134` where low confidence adds caution points.

## BUG-7: Ingredient list not split — "Active ingredients: ..." treated as a single ingredient

**Severity**: High — breaks ingredient-level cross-referencing in the extension UI
**Location**: `backend/src/infrastructure/claude_agent.py:950-953`, `backend/src/infrastructure/trafilatura_extractor.py:84-88,206-229`
**Product**: [Neutrogena Hydro Boost SPF 50 — amazon.ca/dp/B081DJ9KN6](https://www.amazon.ca/dp/B081DJ9KN6)

**What happens**: The extension displays "Ingredients Analyzed (2)" for a product with ~20 individual ingredients. The two "ingredients" are:

1. `"Active ingredients (w/w): Homosalate 4%, Octisalate 4%, Avobenzone 2%, Octocrylene 2%"`
2. `"Inactive ingredients: Blue 1, Caprylyl Methicone, Chlorphenesin, Disodium EDTA, Ethylhexylglycerin, Glycerin, Glyceryl Stearate, Methyl Methacrylate Crosspolymer, Parfum, Pentylene Glycol, Phenoxyethanol, Red 40, Sodium Acryloyldimethyltaurate/VP Crosspolymer, Sodium Hyaluronate, Sodium Hydroxide, Tocopheryl Acetate, Water (eau)"`

The entire comma-separated block is treated as one ingredient entry. This can fail at two layers:

**Layer 1 — Trafilatura extraction** (`trafilatura_extractor.py:206-229`): `_parse_ingredients_text()` strips "Active ingredients:" and "Inactive ingredients:" prefixes via regex (line 212), then splits on `", "` (line 215-217). But for sunscreens, the Amazon HTML has the "Active/Inactive ingredients" format as two separate text nodes in `#important-information .content`. If the selector pulls each node individually, `_parse_ingredients_text` receives `"Active ingredients (w/w): Homosalate 4%, Octisalate 4%, Avobenzone 2%, Octocrylene 2%"` — the regex `active\s+ingredients?\s*[:\-]\s*` (line 212) doesn't match `"Active ingredients (w/w):"` because the `(w/w)` sits between the label and the colon. The prefix isn't stripped, and the entire string is treated as one ingredient.

**Layer 2 — Claude agent** (`claude_agent.py:950-953`): When the extraction pipeline fails to parse ingredients (BUG-5), Claude itself must populate the `ingredients` field. The prompt says `"ingredients": ["complete list from manufacturer website if found, else from product page"]`. Claude sometimes returns the Amazon "Active/Inactive ingredients" text blocks verbatim as 2 array items rather than splitting them into individual ingredients.

**Impact**:

- The ingredient grid in `AnalysisView.svelte` renders 2 huge text blocks instead of 20 individual badges
- Bidirectional cross-referencing (lines 155-178 of `AnalysisView.svelte`) matches ingredient names against allergens/PFAS/concerns using `.includes()` — a massive string like `"Inactive ingredients: ...Phenoxyethanol..."` will match against `"Phenoxyethanol"` in the concerns list, but the _entire block_ gets the `badge-toxic` class, not just that ingredient. All 16 inactive ingredients appear flagged because they share one badge
- The "(2)" count misleads users into thinking only 2 ingredients were analyzed

**Fix**: Two fixes needed:

1. **Trafilatura**: Update the prefix regex in `_parse_ingredients_text()` to handle `"Active ingredients (w/w):"` format — add `(?:\s*\([^)]*\))?` between the label and colon pattern
2. **Claude agent prompt**: Change the `ingredients` instruction from `"complete list"` to explicitly require individual entries: `"ingredients": ["ingredient1", "ingredient2", ...]` with a note: "Each array element must be a single ingredient name. Do NOT include 'Active ingredients:' or 'Inactive ingredients:' prefixes. Split comma-separated lists into individual entries."

## BUG-8: Synchronous Anthropic client blocks the event loop — no concurrent request handling

**Severity**: Critical — server processes one analysis at a time, all other requests queue
**Location**: `backend/src/infrastructure/claude_agent.py:9,110,205,296,721,789`, `backend/src/infrastructure/database.py:9,26`, `backend/Dockerfile:33`, `backend/run.py:7-13`

**What happens**: Three independent issues combine to make concurrent request handling impossible:

### Issue 1: Synchronous Anthropic client in async handler

The Claude agent uses the **synchronous** `Anthropic` client:

```python
# claude_agent.py:9
from anthropic import Anthropic, RateLimitError, APIError

# claude_agent.py:110
self.client = Anthropic(api_key=settings.anthropic_api_key)

# claude_agent.py:205, 296, 721, 789 — all calls are synchronous
response = self.client.messages.create(...)  # ← BLOCKS the event loop
```

The route handler is `async def analyze_product()` (analyze.py:177), which runs on uvicorn's asyncio event loop. When `self.client.messages.create()` is called, it performs **synchronous HTTP I/O** — the entire event loop freezes for 10-60 seconds per Claude API call. During an agentic loop with 5-10 iterations, the event loop is blocked for **minutes**.

Every other request — including health checks, cache hits, and other users' analyses — waits in the queue until the current Claude call returns.

Anthropic provides `AsyncAnthropic` for exactly this case:

```python
from anthropic import AsyncAnthropic
self.client = AsyncAnthropic(api_key=settings.anthropic_api_key)
response = await self.client.messages.create(...)  # ← non-blocking
```

### Issue 2: Synchronous Supabase client

```python
# database.py:9
from supabase import create_client, Client  # ← sync client

# database.py:26
self.client = create_client(settings.supabase_url, settings.supabase_key)
```

All database calls (`self.client.table(...).select(...).execute()`) are synchronous HTTP calls to the Supabase REST API, also blocking the event loop. The `async def` on the DatabaseService methods is misleading — the methods are declared `async` but contain no `await` on actual I/O. They block just like the Anthropic client.

Supabase provides `create_async_client` for async contexts.

### Issue 3: Single uvicorn worker, no worker configuration

```dockerfile
# Dockerfile:33
CMD uvicorn src.api.main:app --host 0.0.0.0 --port ${PORT}
```

```python
# run.py:7-13
uvicorn.run(
    "src.api.main:app",
    host=settings.api_host,
    port=settings.api_port,
    reload=settings.debug,
)
```

No `--workers` flag. Uvicorn defaults to **1 worker process**. Even if the async issues were fixed, a single worker limits CPU-bound throughput. Cloud Run can scale containers, but each container runs only one worker.

**Impact**:

- **Same user, multiple tabs**: User opens 3 Amazon products simultaneously. First analysis starts (takes ~45 seconds of Claude calls). Second and third requests queue behind it. User sees 45s, 90s, 135s response times. The 30/minute rate limit at analyze.py:176 allows the requests through, but they serialize.

- **Multiple users**: User A and User B both click "Analyze" at the same time. User B waits for User A's entire analysis pipeline (scraping + extraction + 5-10 Claude iterations + DB storage) to complete before their request even starts.

- **Health check failures**: Cloud Run sends health probes to `/api/health`. During a 45-second event-loop block from a Claude call, the health endpoint is unreachable. Cloud Run may mark the instance as unhealthy and restart it, killing the in-flight analysis.

**Evidence**: Each analysis involves 5-10 synchronous `client.messages.create()` calls (visible in the logs as iterations 1-8). Each call takes 3-8 seconds. Total blocking time per analysis: 30-60+ seconds. During this entire window, the event loop cannot process any other request.

**Fix**:

1. **Anthropic client**: Switch from `Anthropic` to `AsyncAnthropic`, change all `self.client.messages.create()` to `await self.client.messages.create()`
2. **Supabase client**: Switch from `create_client` to `create_async_client`, add `await` to all DB operations
3. **Uvicorn workers**: Add `--workers 2` (or use Gunicorn with uvicorn workers) to handle CPU-bound work in parallel. For Cloud Run, match to vCPU count.
4. **Request queuing**: Consider adding a background task queue (the unused Celery/Redis in requirements) for long-running analyses, returning a job ID immediately and polling for results

## BUG-9: Supabase security — open RLS policies, SECURITY DEFINER view, mutable function search paths

**Severity**: Critical — publishable anon key can read/write/delete cached data directly
**Location**: Supabase project `staging-ruh` (`vslnwiugfuvquiaafxgh`), all in `public` schema
**Source**: Supabase Database Linter (security advisors scan, 2026-02-08)

**What happens**: The Supabase database has 35 security findings across 4 categories:

### 9a: Three tables with `USING (true)` RLS policies — effectively no security

| Table                 | Policy Name                                 | Rows | Risk                                                                            |
| --------------------- | ------------------------------------------- | ---- | ------------------------------------------------------------------------------- |
| `extracted_content`   | `Allow all operations on extracted_content` | 10   | Anyone with the anon key can read/write/delete all cached web extractions       |
| `ingredient_research` | `service_role_all_access`                   | 0    | Anyone with the anon key can read/write/delete all pre-computed safety research |
| `search_cache`        | `service_role_all_access`                   | 0    | Anyone with the anon key can read/write/delete all cached search results        |

These policies apply to the `public` role (which includes `anon`), using `USING (true)` and `WITH CHECK (true)` for `ALL` operations. The Supabase anon key ships inside the Chrome extension — anyone who inspects the extension source can extract it and call the Supabase REST API directly to query, modify, or delete all data in these tables.

### 9b: SECURITY DEFINER view bypasses RLS

The `cache_statistics` view is defined with `SECURITY DEFINER`, meaning it executes with the **creator's** privileges (typically `postgres` superuser) regardless of who calls it. Any role — including `anon` — that can query this view gets aggregated data from `product_analyses` even if RLS would normally block them.

### 9c: 18 functions with mutable `search_path`

All 18 `public` schema functions lack `SET search_path = ''`. An attacker who can create objects in the `public` schema could shadow system functions (e.g., create a malicious `public.now()`) that gets called instead of `pg_catalog.now()` when these functions run.

Affected functions: `search_allergen`, `search_pfas`, `search_toxic_substance`, `search_reviews`, `search_ingredient_research`, `find_precursors`, `find_metabolites`, `find_product_cache`, `clear_all_cache`, `clear_product_cache`, `clear_product_cache_by_url`, `clear_old_cache`, `cleanup_expired_search_cache`, `cleanup_expired_extractions`, `get_recent_validation_summary`, `get_validation_stats_by_date`, `get_validation_logs_by_product`, `get_most_flagged_substances`

### 9d: 11 tables with RLS enabled but zero policies

| Table                         | Rows | Effect                          |
| ----------------------------- | ---- | ------------------------------- |
| `allergens`                   | 0    | Knowledge base locked out       |
| `pfas_compounds`              | 0    | Knowledge base locked out       |
| `toxic_substances`            | 0    | Knowledge base locked out       |
| `product_analyses`            | 18   | Only accessible via service key |
| `users`                       | 0    | Locked out                      |
| `user_searches`               | 26   | Only accessible via service key |
| `review_chunks`               | 0    | Locked out                      |
| `review_summaries`            | 0    | Locked out                      |
| `alternative_recommendations` | 0    | Locked out                      |
| `user_interactions`           | 0    | Locked out                      |
| `analysis_feedback`           | 0    | Locked out                      |

Currently works because the backend uses the `service_key` (bypasses RLS), but any future anon-key access would silently return 0 rows.

### 9e: Extensions installed in `public` schema

`uuid-ossp` and `vector` are in the `public` schema. Supabase recommends moving them to a dedicated `extensions` schema to avoid namespace pollution and reduce the attack surface for search path injection.

### 9f: Performance — 44 unused indexes, 3 unindexed foreign keys

**Unused indexes** (never been hit since creation): 5 on `validation_logs`, 4 on `review_chunks`, 5 on `ingredient_research`, 5 on `product_analyses`, 3 on `extracted_content`, 2 on `search_cache`, 4 on `pfas_compounds`, 4 on `toxic_substances`, 2 on `alternative_recommendations`, 2 on `user_interactions`, 1 on `analysis_feedback`, 1 on `allergens`, 1 on `review_summaries`, 1 on `user_searches`

**Missing indexes on foreign keys**: `analysis_feedback.user_id`, `user_interactions.search_id`, `user_searches.analysis_id`

**Impact**: Unused indexes consume disk space and slow down writes for zero read benefit. Missing FK indexes will cause sequential scans on DELETE cascades and JOIN queries at scale.

**Fix**: Migration SQL generated at `backend/supabase/migrations/20260208_fix_security_findings.sql`

## Migration Notes

### BUG-9 fix: `service_role` vs `public` RLS policies

Supabase has two built-in PostgREST roles — `anon` (used with the publishable key that ships in the extension) and `service_role` (used with the secret service key held by the backend). The old `USING (true)` policies on `extracted_content`, `ingredient_research`, and `search_cache` were granted to the `public` role, which includes `anon`. This means anyone with the publishable key could call `https://<project>.supabase.co/rest/v1/extracted_content` directly and read/write/delete all rows.

The fix migration (`012_fix_security_findings.sql`) replaces these with `TO service_role` policies — only the backend (holding the service key) can access these tables. The `anon` role gets zero access.

### BUG-9 risk: Extension schema move

Moving `uuid-ossp` and `vector` from `public` to an `extensions` schema (section 9e of the migration) is the **highest-risk step**. If any column defaults reference `uuid-ossp` functions by unqualified name (e.g., `uuid_generate_v4()` instead of `extensions.uuid_generate_v4()`), they need the `extensions` schema in PostgreSQL's `search_path` to resolve. Supabase's default search path includes `extensions`, so this should be transparent — but if any custom `search_path` overrides exist, those references will break silently (new rows get `NULL` instead of a generated UUID, triggering NOT NULL constraint violations).

**Recommendation**: Create a Supabase development branch (`create_branch`) and apply the migration there first. Run a test analysis end-to-end on the branch to verify:

1. `gen_random_uuid()` defaults still fire (not affected — it's from `pgcrypto`, not `uuid-ossp`)
2. `vector` type columns in `review_chunks.embedding` still accept inserts
3. `search_reviews()` RPC still works with the `<=>` cosine distance operator
4. All 18 recreated functions execute without `search_path` errors

Only merge to production after the branch passes all checks.
