⏺ Added as BUG-8. Here's the summary of the three compounding issues:

  The core problem: The server is a single-threaded async Python app where the
  two heaviest I/O operations (Claude API and Supabase) both use synchronous
  clients inside async def handlers. This blocks the event loop entirely.

  ★ Insight ─────────────────────────────────────
  Why async def + synchronous I/O is worse than just using def: If the handler
  were a regular def, FastAPI would automatically run it in a thread pool —
  other requests could still be processed on the event loop while the sync call
  blocks a thread. But because it's async def, FastAPI runs it directly on the 
  event loop, trusting that all I/O is awaited. The synchronous
  client.messages.create() call freezes the entire loop. It's the worst of both
  worlds — declared async but behaving synchronous, with no thread pool escape
  hatch.

  The three layers:
  1. Anthropic() (sync) — each Claude iteration blocks 3-8s, agentic loops block
   30-60s total
  2. create_client() (sync Supabase) — every DB call blocks, including cache
  checks and knowledge base loads
  3. Single uvicorn worker — no process-level parallelism either
  ─────────────────────────────────────────────────

  Ironically, you already have redis and celery in your requirements (noted as
  unused in the audit) — those are exactly the tools for offloading long-running
   analyses to a background queue. The fix is either (a) switch to
  AsyncAnthropic + create_async_client for true async, or (b) use Celery to
  process analyses in background workers and return a job ID to poll.
